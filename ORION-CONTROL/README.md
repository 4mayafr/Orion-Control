# ORION CONTROL

A web-based game community operations and monitoring platform. The website runs in the cloud; a separate worker on your own machine performs Discord integration work and reports results back.

> **Independent community project.** ORION CONTROL is not affiliated with Orion Drift and does not access private infrastructure, internal APIs or server systems. Until you connect an authorised integration, statistics are generated by a mock adapter and **always labelled Simulated**.

## What it does

| Area | Capability |
| --- | --- |
| Overview | Players online, active matches, server health, worker state, recent tasks and activity, player history chart, system status |
| Server statistics | Per-server availability, population, latency, matches; history charts; retrieval timestamps and data provenance |
| Player directory | Searchable directory collected from snapshots, with source labelling |
| Background tasks | Queue, claim, execute, result submission, retries, timeouts, raw + parsed responses, full task detail |
| Discord integration | Guild/channel validation, relay adapter, diagnostics, connection reporting |
| Activity logs | Signed-in actor, action, category, IP and metadata for every audited operation |
| Operators | Roles, per-operator permission overrides, suspension, deletion guards |
| API keys | Worker-scoped keys, hashed at rest, shown once, revocable |
| Settings | Worker offline threshold, task timeout, retention target, integration mode, simulated fallback, password change |

The website works **without** the worker. If the worker is offline, the interface stays available and clearly shows the worker as offline; tasks queue until it returns (then expire after 15 minutes if it does not).

## Architecture

```
┌───────────────────────────────┐          ┌──────────────────────────────┐
│  ORION CONTROL WEB            │          │  ORION CONTROL WORKER        │
│  Next.js · TypeScript         │          │  Node.js · TypeScript        │
│  Vercel (free Hobby plan)     │          │  Chromebook Linux            │
│                               │          │                              │
│  • Auth + permissions         │          │  • Discord.js client         │
│  • Dashboard + stats          │◀─────────│  • Polls for queued tasks    │
│  • Task queue + results       │  HTTPS   │  • Executes integrations     │
│  • Operator + key management  │  outbound│  • Parses Discord responses  │
│  • Audit log                  │─────────▶│  • Sends results/heartbeats  │
└──────────────┬────────────────┘          └──────────────────────────────┘
               │
               ▼
      Hosted PostgreSQL (Neon / Supabase)
```

Key properties:

- **One-way network model.** The worker initiates every request. No inbound port, tunnel or public IP is required for the Chromebook.
- **Queue in the middle.** The website never waits for Discord. It stores a task, returns immediately, and renders the result when the worker submits it.
- **Two storage drivers.** PostgreSQL in production; a zero-config JSON file for local development. The rest of the code only knows the `Store` interface.
- **Server-side authorisation.** Permissions are re-resolved from the database on every page and API call. Hiding a button is never treated as security.

More detail: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Quick start (local, ~15 minutes)

### 1. Install dependencies

From the repository root:

```bash
npm install
```

This also builds the shared TypeScript package (`packages/shared`). If you ever change that package, run `npm run build:shared` (or reinstall), because the website and worker import its compiled output.

### 2. Configure the website

```bash
cp apps/web/.env.example apps/web/.env.local
```

Generate the two secrets and paste them in:

```bash
node -e "console.log('SESSION_SECRET=' + require('crypto').randomBytes(48).toString('base64url'))"
node -e "console.log('INITIAL_ADMIN_SETUP_TOKEN=' + require('crypto').randomBytes(48).toString('base64url'))"
```

For local development you can leave `DATABASE_URL` empty. The website will:
- use a JSON database at `apps/web/.data/orion.json` (git-ignored), and
- seed 30 days of clearly-labelled **simulated** history on first run.

The console prints a warning that local file storage is not persistent.

### 3. Start the website

```bash
npm run dev:web
```

Open <http://localhost:3000>. You will be redirected to `/setup` on a fresh install.

### 4. Create the first administrator

Enter:
- the `INITIAL_ADMIN_SETUP_TOKEN` you generated,
- your name and email,
- a password of at least 10 characters.

Setup is only available while no operator accounts exist. Once created, `/setup` redirects to the sign-in page.

### 5. Create a worker API key

In the dashboard: **API Keys → Create worker key**. Name it `Chromebook worker`, keep the `worker` scope ticked, and copy the key — it is stored as a SHA-256 hash and is shown only once.

### 6. Configure the worker

```bash
cp apps/worker/.env.example apps/worker/.env
```

Set:

```dotenv
ORION_API_URL=http://localhost:3000
ORION_WORKER_KEY=<the key you just copied>
INTEGRATION_MODE=mock
```

`mock` produces simulated data and needs no Discord token. That is the recommended first test.

### 7. Start the worker

In a second terminal:

```bash
npm run dev:worker
```

You should see it start, connect to the API and send heartbeats. The dashboard's worker indicator turns green within ~20 seconds.

### 8. Run the full pipeline

On **Server Statistics**, click **Retrieve statistics**:

1. The website creates a `statistics.retrieve` task (HTTP 202, returns immediately).
2. The worker claims it within ~2 seconds.
3. The mock adapter produces a snapshot marked `source: simulated`.
4. The worker submits the result with raw + parsed payloads.
5. The website stores the snapshot, updates the directory and refreshes the page.

Inspect the whole exchange under **Background Tasks**, including raw and parsed responses. Everything remains labelled **Simulated** until you switch to the real relay mode.

## Running the worker

Development (auto-restart on file changes):

```bash
npm run dev:worker
```

Compiled mode (closer to how you will run it on the Chromebook):

```bash
npm run build --workspace @orion/worker
npm run start --workspace @orion/worker
```

The worker:

- validates its environment at startup and prints exactly which variables are wrong,
- refuses plain `http://` for remote API URLs (the worker key must not travel unencrypted),
- polls the claim endpoint, executes **one task at a time**, and reports results,
- sends heartbeats every 20 seconds (`HEARTBEAT_INTERVAL_MS`),
- spools results to `apps/worker/.data/pending-results.json` when the API is unreachable and replays them later,
- shuts down gracefully on `Ctrl+C` (aborting the current task and flushing state).

To stop it, press `Ctrl+C` or close the terminal. The website remains fully operational.

## Testing website ↔ worker communication

The fastest end-to-end check, without Discord:

1. Start the website and the worker in mock mode (above).
2. Confirm the dashboard shows **Worker online**.
3. **Server Statistics → Retrieve statistics**.
4. **Background Tasks** should show: `running` → `completed`, with duration, raw response and parsed response.
5. **Activity Logs** should record the request and the worker submission.
6. Stop the worker and click **Retrieve statistics** again: the task stays `queued`, the UI warns that the worker is offline. Restart the worker within 15 minutes and the task completes.
7. For an auth check: `curl -s http://localhost:3000/api/worker/tasks/claim -X POST -H 'content-type: application/json' -d '{"workerId":"x"}'` returns `401` (no key).

Optional database verification (PostgreSQL): after a retrieval, `select source, retrieved_at, summary from server_statistics order by retrieved_at desc limit 1;` should show `retrieved` only when using the channel relay; mock data is stored as `simulated`.

## Database

### Local development

No database is required. The JSON file driver at `apps/web/.data/orion.json` implements the same `Store` interface as PostgreSQL and seeds simulated history on first run.

### Production (free tier)

1. Create a free database at [Neon](https://neon.tech) (recommended: serverless-friendly, pooled connection string) or [Supabase](https://supabase.com).
2. Copy the **pooled** PostgreSQL connection string.
3. Put it in `apps/web/.env.local` as `DATABASE_URL` and run:

```bash
npm run db:migrate
```

The runner applies every file in `database/migrations` once, inside a transaction, and records it in `schema_migrations`.

4. Optionally seed simulated history:

```bash
npm run db:seed            # only if the table is empty
npm run db:seed -- --force # add another 30-day block
```

Schema overview:

| Table | Purpose |
| --- | --- |
| `users` | Operator accounts, role, status, bcrypt password hash |
| `permissions` | Per-operator permission overrides (grant/revoke) |
| `background_tasks` | Task queue, status, timestamps, payload, raw/parsed result, error |
| `task_results` | Immutable history of every worker submission (including retries) |
| `server_statistics` | Snapshots with source, summary, servers, matches, players |
| `players` | Upserted player directory |
| `activity_logs` | Audit trail |
| `worker_status` | Latest heartbeat per worker |
| `api_keys` | SHA-256 hashed worker keys, scopes, revocation |
| `integration_settings` | System settings (key → JSON value) |

Indexes cover task status/created time, active-task deduplication, statistics recency, logs and key hashes. See [database/migrations/0001_init.sql](database/migrations/0001_init.sql).

## Background task lifecycle

```
queued ──claim──▶ running ──result──▶ completed
   │                 │
   │                 ├──failure with attempts left──▶ queued (retry)
   │                 ├──failure, attempts exhausted──▶ failed
   │                 └──no result before timeout─────▶ timed_out (retry once)
   │
   └──not claimed within 15 min──▶ timed_out
```

- **Duplicate prevention:** a partial unique index on `dedupe_key` allows only one active task per type. Two operators clicking “Retrieve” share one task.
- **Atomic claiming:** `SELECT … FOR UPDATE SKIP LOCKED` ensures exactly one worker receives each task.
- **Ownership:** results are accepted only from the worker that claimed the task, and only while it is `running`. Duplicate submissions are rejected.
- **Timeouts:** the server reaps stale running tasks (default 60 s) and requeues once if attempts remain; otherwise marks them `timed_out`.
- **Retries:** a retryable failure requeues the task with the attempt count preserved. Manual retry resets the count.
- **Raw responses:** preserved for successful and failed executions, so unparseable Discord replies can be diagnosed.
- **Reaper:** runs lazily on task endpoints and once daily via Vercel Cron (`/api/maintenance/reap`).

Every task stores: unique ID, type, status, requesting operator, creation/start/completion timestamps, duration, attempts, timeout, worker id, error code/message, raw response and parsed response.

## Discord integration and its limitation

The worker connects with Discord.js using the non-privileged `Guilds` and `GuildMessages` intents (plus `MessageContent` only if you explicitly enable it), validates that the configured channel belongs to the configured guild, and requires View Channel + Send Messages.

**Important:** Discord bots cannot invoke another bot's slash commands. Interactions are created by users; there is no supported API for bot-triggered application commands. Self-bots and token impersonation violate Discord's Terms of Service and are not implemented.

The worker therefore provides a **channel relay**: it posts a marked request into your private channel and parses the response posted by an authorised integration bot (optionally pinned with `DISCORD_TARGET_BOT_ID`). This works if the target bot has an official API/webhook, supports being relayed to, or you operate the integration yourself. If the target bot has no such mechanism, automated retrieval is not possible — the mock adapter keeps the pipeline testable and every result stays labelled Simulated.

Full protocol, supported response formats (JSON, pipe-separated rows, key/value totals) and troubleshooting: [docs/DISCORD.md](docs/DISCORD.md).

## Simulated, retrieved and unavailable data

| Label | Meaning |
| --- | --- |
| **Simulated** | Produced by the mock adapter or the seed script. Not a genuine read-out. Stored with `source = 'simulated'` |
| **Retrieved** | Parsed from an authorised integration response and validated against the shared schema. Stored with `source = 'retrieved'` |
| **Unavailable** | Nothing has been collected. The UI shows an empty state instead of inventing numbers |

If no statistics exist and simulated fallback is enabled, the dashboard shows a **transient in-memory placeholder** that is explicitly labelled and never written to the database. The Settings page can disable it.

## Security model

- **Sessions:** HS256 JWT in an HttpOnly, SameSite=Lax cookie (Secure in production), 8-hour expiry, rotated on login.
- **Passwords:** bcrypt cost 12; minimum 10 characters; no public registration.
- **Bootstrap:** `/setup` requires `INITIAL_ADMIN_SETUP_TOKEN` and works only while zero operators exist.
- **Authorisation:** every page and API route re-resolves role + overrides from the database. Suspension takes effect on the next request.
- **CSRF:** cookie-authenticated mutations require a same-origin `Origin` header when the browser sends one.
- **Worker auth:** bearer key, hashed with SHA-256 at rest, worker scope required, revocation is immediate.
- **Transport:** remote `ORION_API_URL` must be HTTPS; the worker never listens on a port.
- **Secrets:** Discord tokens and worker keys live only in the worker environment. Nothing under `NEXT_PUBLIC_` is secret.
- **Rate limiting:** login (8 attempts / 5 min per IP) and setup. In-memory per instance, so it is a speed bump rather than a distributed quota.
- **Audit:** sign-ins, failures, task lifecycle, operator changes, key creation/revocation and settings changes are logged.
- **Last-admin guards:** cannot suspend, demote or delete the final active administrator, nor delete yourself.

## Deploying to Vercel (steps 4–10)

Detailed walkthrough with screenshots-free step numbering: [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

### 4. Create a GitHub repository

```bash
git init
git add .
git commit -m "Initial ORION CONTROL implementation"
# create an empty repository on GitHub named orion-control, then:
git remote add origin https://github.com/<you>/orion-control.git
git branch -M main
git push -u origin main
```

Confirm that `.env`, `.env.local` and `.data/` are **not** committed.

### 5. Import into Vercel

1. Vercel → **Add New → Project** → import the repository.
2. **Root Directory:** `apps/web` (important — this is a monorepo).
3. Framework preset: Next.js. Leave the build command as `npm run build`; the package's `prebuild` builds the shared package.
4. Deploy.

### 6. Configure Vercel environment variables

In **Project → Settings → Environment Variables** add for Production (and Preview if desired):

```
DATABASE_URL=postgresql://…pooler…/orion?sslmode=require
SESSION_SECRET=<48-byte base64url secret>
INITIAL_ADMIN_SETUP_TOKEN=<one-time secret>
CRON_SECRET=<random secret>        # optional but recommended for /api/maintenance/reap
```

Then **redeploy** so they take effect.

### 7. Apply migrations to production

From your machine, with the production connection string temporarily in `apps/web/.env.local`:

```bash
npm run db:migrate
```

Never commit that file. After migrating, open `https://<project>.vercel.app/setup` and create the administrator.

### 8. Configure the Chromebook worker

In the ChromeOS Linux container:

```bash
sudo apt update && sudo apt install -y git
# install Node 20+ (nvm is simplest: https://github.com/nvm-sh/nvm)
git clone https://github.com/<you>/orion-control.git
cd orion-control
npm install
cp apps/worker/.env.example apps/worker/.env
```

Edit `apps/worker/.env`:

```dotenv
ORION_API_URL=https://<project>.vercel.app
ORION_WORKER_KEY=<key from the deployed dashboard>
INTEGRATION_MODE=channel
DISCORD_BOT_TOKEN=<bot token>
DISCORD_GUILD_ID=<guild id>
DISCORD_CHANNEL_ID=<private channel id>
DISCORD_TARGET_BOT_ID=<optional target bot id>
```

Then build and start:

```bash
npm run build --workspace @orion/worker
npm run start --workspace @orion/worker
```

### 9. Keep the worker running

For a long-running session:

```bash
nohup npm run start --workspace @orion/worker > worker.log 2>&1 &
```

ChromeOS suspends the Linux container when the Chromebook sleeps, so the worker goes offline; the website remains available and the dashboard reports the worker offline. Restart the worker when the machine wakes.

### 10. Test communication

1. Dashboard shows **Worker online** within ~20 seconds (heartbeat).
2. **Server Statistics → Retrieve statistics** → status moves queued → running → completed.
3. Task detail shows the parsed snapshot and raw Discord response.
4. Run **Discord Integration → Run channel diagnostics** to confirm the bot resolved the guild/channel.
5. Revoke the worker key under **API Keys** and watch the worker log `401` responses — rotate the key and restart the worker.

If anything fails, see [Troubleshooting](#troubleshooting) and the API reference in [docs/API.md](docs/API.md).

## Free-tier limits

| Service | Limit to keep in mind |
| --- | --- |
| **Vercel Hobby** | Cron jobs run at most once per day (used only for task reaping); serverless functions are short-lived, so the website never waits for Discord; commercial usage is not permitted on Hobby |

## Troubleshooting

**`DATABASE_URL is not set` on the dashboard (deployed)**
Create a free PostgreSQL database and add `DATABASE_URL` in Vercel. Local file storage is deliberately refused on Vercel because serverless disks are ephemeral.

**Login page says “Database unavailable”**
`DATABASE_URL` is wrong or migrations have not run. Run `npm run db:migrate` and check the connection string uses the pooled host.

**Worker exits with “configuration is incomplete”**
The message lists each invalid variable. Copy `apps/worker/.env.example` and fill in the required values. In `channel` mode, Discord credentials are mandatory.

**Dashboard shows worker offline while the worker is running**
Check the worker log for heartbeat failures. Confirm `ORION_API_URL` points at the deployed URL and that the worker key is active (not revoked). The offline threshold is 90 seconds by default and configurable in Settings.

**Task stuck in `queued`**
The worker is offline or cannot claim. Tasks expire after 15 minutes (`TASK_EXPIRED`). Restart the worker; the next poll claims queued work.

**Task `failed` with `UNPARSED_RESPONSE`**
The Discord reply did not match any supported format. Open the task's raw response and adapt the response format or the parser. ORION CONTROL never fills unknown fields with invented values.

**`RESPONSE_TIMEOUT` in channel mode**
No authorised bot replied within the timeout. Confirm the integration posts in the configured channel, and that `DISCORD_TARGET_BOT_ID` (if set) matches the responder. Slash commands cannot be triggered by a bot — see [docs/DISCORD.md](docs/DISCORD.md).

**Repeated `401 WORKER_KEY_INVALID`**
The key was revoked or belongs to another deployment. Create a new worker-scoped key and update `apps/worker/.env`.

**Local changes to shared types are not picked up**
Run `npm run build:shared` (the shared package is consumed from its compiled `dist`). Because Next bundles the shared package at build time, rebuild/restart the website after changing it.

**Local edits to the demo data keep reappearing**
The JSON file driver caches the document in memory per process and rewrites it on each change. Stop every website process before editing `apps/web/.data/orion.json`; run only one website process against the file driver.

## Current scope and unfinished work

Deliberately **not** implemented (documented rather than faked):

- **Direct bot-to-bot command invocation** — impossible on Discord; a relay adapter is provided instead.
- **Automatic task/log pruning** — `taskRetentionDays` is stored but nothing is deleted automatically; the file driver caps local logs at 5 000 entries.
- **Self-service password reset / per-session revocation** — accounts are reset by an administrator (Operators → set a new password). Sessions are stateless and expire after 8 hours; changing a password does not invalidate other sessions immediately.
- **`station.create`** — the permission exists in the model but station management screens are not part of this build.
- **Distributed rate limiting** — the limiter is per serverless instance.
- **Real Orion Drift telemetry** — no private integration is assumed or attempted.

Assigning `station.create` or building station management is a natural next phase; the permission already flows through the role/override system.
